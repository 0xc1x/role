# Anuncios y avisos importantes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un operador publica un mensaje desde el panel de admin y el consumidor lo ve al abrir la app; el obligatorio se puede cerrar pero vuelve hasta que se acknowledge.

**Architecture:** Tabla `announcements` (contenido del operador) + `announcement_acknowledgements` (estado de lectura del `required`). La lectura de mobile es **Supabase directo con RLS como frontera** — el móvil no pasa por la API, igual que el resto de sus features. La API solo existe para que el operador publique y para el banner de landing. La elegibilidad (ventana, audiencia) vive **enteramente en la política RLS**; el cliente solo decide qué mostrar primero y qué agrupar.

**Tech Stack:** Postgres + RLS · `@0c1x/role-commons` (zod) · NestJS 11 · TanStack Start (admin) · Expo SDK 57 + expo-router (mobile) · bun:test · Playwright

**Spec:** `docs/superpowers/specs/2026-10-03-anuncios-design.md` — el plan razona desde el spec y ambos viajan juntos.

## Global Constraints

- **Toda migración entra por `apply_migration`.** Nunca por `execute_sql` ni por el dashboard. Después de aplicar: renombrar el archivo a la versión que asignó el servidor y confirmar que `md5sum` del archivo == `md5(statements[1])` del ledger `supabase_migrations.schema_migrations`. Detalle en `supabase/migrations/README.md`.
- **`severity` es `text` con `CHECK`, no enum de Postgres.** Mismo criterio que `app_store.state`: un enum obliga a migrar cada vez que aparece un valor.
- **Los valores de las columnas son en inglés** (`info`, `required`, `all`, `consumers`, `businesses`, `specific`); el copy de UI es es-ES y vive en `strings.ts` de mobile.
- **Cero literales inline en pantallas de mobile.** Todo copy en `src/core/i18n/strings.ts`.
- **Comentarios en español** en `src/`. La capa de tests e2e es inglés.
- **Prohibido `as` para callar al typechecker.** Si hace falta un tipo no vacío, se expresa en el tipo (ver `AuthorPalette` de `packages/commons` para el patrón).
- **La apertura de la app no depende de esta consulta.** Un fallo deja la pantalla vacía y la app abre igual.
- **`tips` no se toca.** Tiene 3 filas activas y UI en Explorar; ver §3 del spec.

## Review Focus

Cinco modos de falla que el spec implica pero que ninguna tarea ejercita, ordenados por probabilidad de morder a una persona:

1. **`body` con HTML en el banner de landing.** El landing renderiza en un navegador; mobile con `Text` no corre riesgo, landing sí. Se espera texto plano, nunca markup interpretado.
2. **`required` alcanzado por un usuario anónimo.** No hay `user_id` sin sesión, así que no se puede acknowledge y volvería en cada apertura, para siempre. Se espera: un `required` nunca se entrega a un anónimo.
3. **Editar un `required` ya entendido.** El ack es por `(announcement_id, user_id)`, así que editar el texto no lo vuelve a mostrar. Es lo correcto -- re-notificar en cada edición es peor -- pero tiene que estar fijado por un test, no por casualidad.
4. **`audience_kind = 'specific'` con las dos listas vacías.** El aviso queda activo en el panel y no lo ve nadie. Es un no-op silencioso: el form tiene que impedirlo.
5. **`start_at` en el futuro.** No debe aparecer antes de tiempo. Lo cubre RLS con `now()` del servidor, no un filtro del cliente.

- [ ] **Step 3: Aplicar la migración**

Contenido, en este orden:

```sql
create table public.announcements (
  id uuid primary key default gen_random_uuid(),
  title text not null check (char_length(title) between 3 and 120),
  body text not null check (char_length(body) between 3 and 2000),
  severity text not null check (severity in ('info', 'required')),
  audience_kind text not null check (audience_kind in ('all', 'consumers', 'businesses', 'specific')),
  user_ids uuid[] not null default '{}',
  business_ids uuid[] not null default '{}',
  priority integer not null default 0,
  active boolean not null default true,
  start_at timestamptz,
  end_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Luego `announcement_acknowledgements` con PK compuesta `(announcement_id, user_id)`, dos FK con `on delete cascade`, y `acknowledged_at timestamptz not null default now()`.

Índices: `(active, priority desc, created_at desc) where active`, y `gin (user_ids)`, `gin (business_ids)`.

RLS habilitado en las dos, con `force row level security` si es el patrón del repo (verificar en `enable-rls.rls.db.spec.ts`).

Política de select de `announcements` — la elegibilidad entera, sin fallback de cliente:

```sql
using (
  active
  and (start_at is null or now() >= start_at)
  and (end_at is null or now() < end_at)
  and (severity = 'info' or auth.uid() is not null)
  and (
        audience_kind = 'all'
     or (audience_kind = 'consumers' and auth_helpers.my_role() = 'user')
     or (audience_kind = 'businesses' and auth_helpers.my_role() = 'business')
     or user_ids @> array[auth.uid()]
  )
)
```

El fragmento `severity = 'info' or auth.uid() is not null` es la regla del Review Focus #2: sin él, un `required` llegaría a un anónimo que no puede acknowledge.

`announcement_acknowledgements`: `select` e `insert` con `user_id = auth.uid()`. **Sin `update` ni `delete`** — no hay forma de des-acknowledgear.

Aplicar con `apply_migration`, renombrar el archivo a la versión que asignó el servidor, y probar el md5 contra el ledger.
